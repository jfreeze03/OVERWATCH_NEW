## What it adds and why

The reconcile-scheduling changes (serialize the daily fan-out, retarget the
nightly reconcile, de-collide the 06:30–06:50 root tasks) can't be sized safely
from code alone — `MART_TASK_GRAPH_DAILY` keeps only per-*pipeline* wall time and
discards `SCHEDULED_TIME`. V058 adds the missing per-**node** signal:

- **`MART_TASK_NODE_DAILY`** (DAY × DATABASE × SCHEMA × TASK_NAME): `RUNS`,
  `FAILED`, `AVG/P95/MAX_QUEUE_SEC` (the `SCHEDULED_TIME→QUERY_START_TIME` dispatch
  delay — the exact signal that quantifies 06:40/06:45 XSMALL contention),
  `AVG/P95/MAX_EXEC_SEC`, `FIRST_START`, `LAST_COMPLETED`, `LOAD_TS`.
- **`SP_LOAD_MARTS_V27`** gains one new standalone guarded arm `[6b]` after the
  task-graph arm: one extra `TASK_HISTORY` scan at the same `-:d` window, its own
  `BEGIN…EXCEPTION`, MERGE-keyed on the grain (idempotent). Every existing statement
  is byte-identical (a CI test proves it).

The table fills on the **existing** cadence — `TASK_LOAD_MARTS_V27_HOURLY` calls
`('HOURLY',2)`; the nightly reconcile calls `('HOURLY',3)` — both reaching back over
that morning's runs. Per-node **credits** are intentionally out of scope (arm [6]
already carries pipeline-grain credits); a fast-follow if the reconcile analysis
needs them.

## Payoff — sizing the deferred schedule work (after 2–4 mornings)

```sql
SELECT TASK_NAME, MAX(RUNS) AS runs, ROUND(AVG(AVG_QUEUE_SEC),1) AS avg_queue_s,
       MAX(MAX_QUEUE_SEC) AS max_queue_s, ROUND(AVG(AVG_EXEC_SEC),1) AS avg_exec_s,
       MAX(MAX_EXEC_SEC) AS max_exec_s
FROM DBA_MAINT_DB.OVERWATCH.MART_TASK_NODE_DAILY
WHERE TASK_NAME IN ('TASK_LOAD_DAILY','TASK_NIGHTLY_RECONCILE','TASK_LOAD_OBJECT_COST',
                    'TASK_ANOMALY_SWEEP','TASK_WAREHOUSE_CHANGE_SCAN','TASK_LOAD_MARTS_V27_DAILY')
GROUP BY TASK_NAME ORDER BY max_queue_s DESC;
```

`max_queue_s` reveals which tasks actually contend for the XSMALL (sizes the
de-collision), and `avg/max_exec_s` gives the durations needed to order a
serialized fan-out chain and confirm it fits before the next hourly cron.

## Rollback

Purely additive; no task-graph state to restore. Reverse: re-derive
`SP_LOAD_MARTS_V27` back to the V057 bytes and `CREATE OR REPLACE PROCEDURE` it
(no task needs suspending), then `DROP TABLE IF EXISTS
DBA_MAINT_DB.OVERWATCH.MART_TASK_NODE_DAILY;`, and lower the lockstep artifacts
(validate.sql floor to 57, drop the admin `_EXPECTED_MIGRATIONS[58]` entry,
regenerate the rebuild bundle). No existing mart loses data — the new arm only
writes the new table, and its own `EXCEPTION` guard already isolates it in
production, so an emergency full rollback is rarely needed.
