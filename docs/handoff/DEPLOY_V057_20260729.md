# Deploy runbook — V057 — 2026-07-29

One worksheet, Snowsight, off-peak. Prereq: V056 applied
(`SELECT MAX(VERSION) FROM DBA_MAINT_DB.OVERWATCH.SCHEMA_VERSION;` = 56).

Low-risk: **one** proc re-derivation (`SP_LOAD_MARTS_V27`), no schema change, no
new object, no first-fill. A **correctness** fix — four failure-count columns
were a constant 0.

## What it fixes

`SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY.EXECUTION_STATUS` takes the values
`success` / `fail` / `incident`, and `OW_QH_EXTRACT` copies it verbatim, so a
failed query is stored as `'FAIL'` — never `'FAILED'`. Four HOURLY arms of
`SP_LOAD_MARTS_V27` counted failures with `EXECUTION_STATUS = 'FAILED'`, which
never matches, so the `FAILS` column was stuck at 0 in:

- **MART_WAREHOUSE_EFFICIENCY_DAILY** (efficiency arm)
- **MART_QUERY_FAMILY_DAILY** (query-family arm)
- **FACT_QUERY_ROLE_HOURLY** (role-hour arm)
- **FACT_QUERY_SCHEMA_HOURLY** (schema-hour arm)

V057 changes those four predicates to `= 'FAIL'`, matching the primary facts
(`FACT_QUERY_HOURLY` / `FACT_QUERY_DAILY` / `OPS_DIAG` already use `'FAIL'`). The
task-graph arm's `STATE = 'FAILED'` predicates read `TASK_HISTORY`, whose states
genuinely are `'FAILED'` — those are deliberately left untouched.

The paired app-side instance (`change_impact_sql.warehouse_daily_series`, the
per-warehouse change chart over live `QUERY_HISTORY`) is fixed in the same
release (`<> 'SUCCESS'`); no deploy step — it ships with the app.

## Pre-flight (confirm the domain BEFORE applying)

```sql
-- The whole fix rests on the stored value being 'FAIL', not 'FAILED'. Confirm:
SELECT EXECUTION_STATUS, COUNT(*) AS n
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE START_TIME >= DATEADD('day', -2, CURRENT_TIMESTAMP())
GROUP BY 1 ORDER BY n DESC;
-- Expect SUCCESS / FAIL / INCIDENT. If you ever see a literal 'FAILED' row here,
-- STOP and flag it — this migration would then be wrong for this account.
```

## Verify

```sql
-- 1. Version: expect 57
SELECT MAX(VERSION) FROM DBA_MAINT_DB.OVERWATCH.SCHEMA_VERSION;

-- 2. After the next hourly load, a recent day with real failures should now
--    show FAILS > 0 (was a constant 0). Approximate cross-check against the
--    primary fact, which was always correct:
SELECT e.DAY,
       SUM(e.FAILS)          AS eff_fails,      -- MART_WAREHOUSE_EFFICIENCY_DAILY
       SUM(d.FAILED_COUNT)   AS fact_fails      -- FACT_QUERY_DAILY (reference)
FROM DBA_MAINT_DB.OVERWATCH.MART_WAREHOUSE_EFFICIENCY_DAILY e
LEFT JOIN (SELECT DAY, SUM(FAILED_COUNT) AS FAILED_COUNT
           FROM DBA_MAINT_DB.OVERWATCH.FACT_QUERY_DAILY GROUP BY DAY) d
  ON d.DAY = e.DAY
WHERE e.DAY >= DATEADD('day', -3, CURRENT_DATE())
GROUP BY e.DAY ORDER BY e.DAY;
-- The point is eff_fails flips from a hard 0 to a real count in the same
-- ballpark as fact_fails (both count the 'FAIL' token). Do NOT expect exact
-- equality: the efficiency mart filters WAREHOUSE_NAME IS NOT NULL and reads a
-- rolling -:d window, while FACT_QUERY_DAILY includes NULL-warehouse queries on
-- a day-aligned window — so small day-level differences are expected and fine.
```

Then `snowflake/validate.sql` — top row reads `V001..V057 applied`.

## Correcting history

The fix corrects data **going forward** from the next hourly load; the nightly
reconcile repairs the trailing days automatically (efficiency / role-hour /
schema-hour rebuild from live `QUERY_HISTORY` at `d=3`; the query-family mart
from the 72h extract at `d=2`). Rows already written with `FAILS=0` before V057
keep that 0 until reloaded.

To correct older history in one pass, re-run the marts for a wider window
off-peak — for example:

```sql
CALL DBA_MAINT_DB.OVERWATCH.SP_LOAD_MARTS_V27('HOURLY', 90);
```

`MART_WAREHOUSE_EFFICIENCY_DAILY`, `FACT_QUERY_ROLE_HOURLY` and
`FACT_QUERY_SCHEMA_HOURLY` read live `QUERY_HISTORY`, so they rebuild the full
requested window. `MART_QUERY_FAMILY_DAILY` is extract-fed (capped at
`LEAST(:d, 2)`), so its deep history is only corrected as far back as
`OW_QH_EXTRACT` reaches (~2 whole days) unless a `snowflake/backfill_365.sql` run
re-fills the extract first.

## Rollback

`SP_LOAD_MARTS_V27` is `CREATE OR REPLACE`; re-run the V056 definition to revert
(it re-introduces the `FAILS=0` behavior). No data is deleted by this migration.
