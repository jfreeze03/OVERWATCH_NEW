# Deploy runbook — V052 (2026-07-27)

One worksheet, Snowsight, off-peak. Prereq: V051 applied
(`SELECT MAX(VERSION) FROM DBA_MAINT_DB.OVERWATCH.SCHEMA_VERSION;` = 51).

## What it does

`snowflake/migrations/V052__exec_board_windows_180_365.sql` — re-derives
`SP_REFRESH_EXEC_BOARD` to compute two more windows (180, 365) so Overview's
KPI board has rows for the new filter options, then reloads the board. No new
objects. The board reads long-retention facts, so the new windows are history,
not a live rescan.

The app side (already committed) adds 180/365 to the window picker; the picker
discloses that beyond 90 days only mart-history panels (Overview KPIs, storage,
chargeback) and Cortex user costs honor the window — other live scans stay
capped at 90.

## Run

1. Paste and Run All: `snowflake/migrations/V052__exec_board_windows_180_365.sql`
   - guard passes (51 ≥ 51); `CREATE OR REPLACE` swaps the proc; the `CALL`
     populates the 180/365 board rows; `SCHEMA_VERSION` → 52.

## Verify

```sql
-- 1. Version: expect 52
SELECT MAX(VERSION) FROM DBA_MAINT_DB.OVERWATCH.SCHEMA_VERSION;

-- 2. The board now has 180 and 365 window rows:
SELECT WINDOW_DAYS, COUNT(*) AS ROWS_
FROM DBA_MAINT_DB.OVERWATCH.MART_EXEC_BOARD
GROUP BY WINDOW_DAYS ORDER BY WINDOW_DAYS;
-- expect rows for 7,14,30,60,90,180,365
```

Then in the app: pick 180 or 365 in the window filter — Overview KPIs, storage,
chargeback, and the Cortex user-cost tab (Chargeback & AI → AI users) show the
long window; the filter caption notes live scans cap at 90.

## Rollback

Idempotent, `CREATE OR REPLACE`. To revert the proc to its 5-window form,
re-run V045's `SP_REFRESH_EXEC_BOARD` block; the 180/365 board rows age out on
the next daily reload. (You'd also revert the app's DAY_WINDOW_OPTIONS.)
