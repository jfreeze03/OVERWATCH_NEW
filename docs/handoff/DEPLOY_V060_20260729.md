## What it fixes

- **#5 COMPILE_PCT > 100%.** `MART_QUERY_FAMILY_DAILY` had no wall-clock column,
  so the compile-heavy panel divided total compile time by EXECUTION-only time.
  V060 adds `TOTAL_ELAPSED_SEC` (additive, NULL for history) and the loader
  stores it; the app reader (ships with v4.70.0) bounds COMPILE_PCT on it and
  degrades pre-V060 rows to the old exec basis.
- **#11 schema-filtered Queued under-reported.** `FACT_QUERY_SCHEMA_HOURLY`
  summed overload-queue time only; now OVERLOAD + PROVISIONING, matching
  `FACT_QUERY_HOURLY` and the query-window contract.
- **CS-alert pseudo-warehouse guard.** `COST_CLOUD_SVC_RATIO`'s metering
  subquery gains `WAREHOUSE_ID > 0` so `CLOUD_SERVICES_ONLY` (ratio = 100%)
  can never fire the alert.

## Verify

```sql
-- 1. Version: expect 60
SELECT MAX(VERSION) FROM DBA_MAINT_DB.OVERWATCH.SCHEMA_VERSION;

-- 2. Column exists (NULL for history is expected):
SELECT COUNT(*) AS rows_total, COUNT(TOTAL_ELAPSED_SEC) AS rows_with_elapsed
FROM DBA_MAINT_DB.OVERWATCH.MART_QUERY_FAMILY_DAILY;

-- 3. Smoke the loader, then confirm new rows carry wall-clock >= exec time:
CALL DBA_MAINT_DB.OVERWATCH.SP_LOAD_MARTS_V27('HOURLY', 2);
SELECT DAY, COUNT(*) AS fams,
       COUNT_IF(TOTAL_ELAPSED_SEC IS NOT NULL) AS with_elapsed,
       COUNT_IF(TOTAL_ELAPSED_SEC < TOTAL_EXEC_SEC) AS anomalies   -- expect ~0
FROM DBA_MAINT_DB.OVERWATCH.MART_QUERY_FAMILY_DAILY
WHERE DAY >= DATEADD('day', -2, CURRENT_DATE())
GROUP BY DAY ORDER BY DAY;

-- 4. Schema-hourly queued now includes provisioning (values can only grow):
SELECT MAX(LOAD_TS) FROM DBA_MAINT_DB.OVERWATCH.FACT_QUERY_SCHEMA_HOURLY;

-- 5. Alert guard: the pseudo-warehouse can no longer fire the CS alert.
CALL DBA_MAINT_DB.OVERWATCH.SP_ALERT_SCAN();
SELECT TITLE FROM DBA_MAINT_DB.OVERWATCH.ALERT_EVENTS
WHERE RULE_ID = 'COST_CLOUD_SVC_RATIO'
  AND TITLE ILIKE '%CLOUD_SERVICES_ONLY%'
  AND RAISED_AT >= DATEADD('hour', -1, CURRENT_TIMESTAMP());       -- expect zero rows
```

## History note

Only the trailing ~2 days of the qfam/schema marts ever re-load, so older rows
keep NULL `TOTAL_ELAPSED_SEC` (the app degrades them to the exec basis, labeled
in code) and overload-only `QUEUED_SEC`. Correcting deep history would need an
extract backfill first (`snowflake/backfill_365.sql`) — optional, not required.

## Rollback

Both procs are `CREATE OR REPLACE` — re-run the V059 (marts) / V056 (alert)
definitions to revert. The added column is inert if unpopulated; leave it (a
DROP COLUMN would break the v4.70.0 reader's COALESCE — roll the app back first
if you truly need to remove it). No data is deleted.
