## 1. [HIGH / CONFIRMED] Right-sizing simulator — resize savings estimate & savings-ledger booking
**`app/ui/pages/cost_parts/optimize.py:216`**

**Defect:** Resize savings branch is gated on RECOMMENDATION.upper().startswith("DOWN"), but size_recommendations emits "Size down candidate" (uppercases to "SIZE DOWN CANDIDATE"), so the branch is dead and est_sz stays 0.0 for every resize.

**Failure scenario:** DBA selects a genuine size-down candidate (RECOMMENDATION=="Size down candidate", MONTHLY_USD_NOW=$4,000, SCENARIO_DOWN_USD=$2,000) and clicks 'Execute resize + log'. **Verify reasoning:** sizing.py:22 defines RECOMMEND_DOWN='Size down candidate'; size_recommendations (sizing.py:50-72) is the only producer of the RECOMMENDATION column and can only emit one of four constants — 'Size up / add cluster', 'Size down candidate', 'Tune auto-suspend first', 'Keep'. srow at optimize.py:210 is a row of that same `sized` frame, so srow['RECOMMENDATION'] is always one of those four. Downstream at lines 219 (caption), 232 (sql_number(est_sz) -> 0), and 237 (`if ok and est_sz > 0` -> skips SAVINGS_LEDGER insert) reproduce the reported wrong outputs. Fix is `'DOWN' in ...` or `.startswith('SIZE DOWN')`.

## 6. [HIGH / CONFIRMED] FACT_QUERY_DAILY (day-grain query fact; feeds exec-board query-volume windows)
**`snowflake/migrations/V042__codex_r22.sql:203`**

**Defect:** The trailing FACT_QUERY_DAILY MERGE re-aggregates the oldest calendar day in a now-72h window and overwrites its previously-complete row with a shrinking partial, freezing every aging day at ~its last hour of activity.

**Failure scenario:** Warehouse runs 10,000 queries on 2026-07-25 (day K). On days K, K+1, K+2 the hourly MERGE window (>= DATEADD('day',-3,CURRENT_TIMESTAMP())) fully covers K -> FACT_QUERY_DAILY[K]=10,000 correct. On K+4 the window no longer reaches K, the source has no K row, and K is frozen. backfill_365 (START_TIME < MIN(DAY), one-time) never repairs it; no other proc writes FACT_QUERY_DAILY. The partial is guaranteed by the WHERE clock bound independent of extract retention. Exec-board/score readers summing FACT_QUERY_DAILY over 7/30/90/180/365-day windows undercount query volume by ~95% for every day older than ~2 days.

**Verify reasoning:** Independently reproduced from first principles. The MERGE UPDATE at V042 209-212 (identical live code in V055 257-260, carried forward verbatim) overwrites rather than accumulates, and the source WHERE at line 203/V055 251 restricts to now-72h, so the oldest calendar day is structurally partial each run and freezes once it leaves the window. Verified no healing path: SP_LOAD_DAILY_FACTS (V045 50) does not touch FACT_QUERY_DAILY; backfill_365.sql line 131 guard fills only days below MIN(DAY); SP_NIGHTLY_RECONCILE re-runs the same partial MERGE. Matches CLAUDE.md's explicit bug definition ('a trailing-window MERGE that overwrites an aging day with a partial aggregate freezes it undercounted'). Note: the cited V042 is superseded by an identical V055 SP_LOAD_QH_EXTRACT; the defect is the pre-existing V042 loader logic, not V055's cloud-services change, so it is in scope.
