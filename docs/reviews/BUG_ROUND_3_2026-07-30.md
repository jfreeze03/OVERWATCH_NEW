## MEDIUM

### R3-1 [MEDIUM · CONFIRMED] Control Room triage "nothing to triage" hides a failed spend-anomaly source
`app/ui/pages/control_room.py:417`
When `FACT_WAREHOUSE_DAILY` fails to load (mart cold / transient) AND there happen to be no open
alerts or task failures, `anomalies=[]`, the queue is empty, and `sources_ok = alerts.ok and
tasks.ok` — which **never checks `wh_daily.ok`** — so the flagship morning screen prints the green
"Nothing to triage: no open alerts, task failures, or spend anomalies in scope." A real
runaway-warehouse day is invisible behind an all-green banner; `run()` only buffers the error.
**Fix:** `sources_ok = alerts.ok and tasks.ok and wh_daily.ok`; add a spend-anomaly clause to the
else-branch (`:420-423`) so a failed read demotes the all-clear to the incomplete-inputs banner.

### R3-2 [MEDIUM · CONFIRMED] Query-inspector cache % is off by 100× (missing the fraction→percent ×100)
`app/data/insights_sql.py:332` → rendered `app/ui/pages/operations.py:213`
`query_detail()` selects `PERCENTAGE_SCANNED_FROM_CACHE AS CACHE_PCT` raw (a 0-1 fraction) and the
drill-in renders `{…:,.0f}% cache`. A 0.85-cache query shows "1% cache", fully cached "1%", cold
"0%" — warm vs cold indistinguishable. Violates the house rule (×100 at read; sibling
`insights_sql.py:96` and the mart readers `mart_sql.py:315` / `mart27_sql.py:275` all do it).
**Fix:** select `PERCENTAGE_SCANNED_FROM_CACHE * 100 AS CACHE_PCT` (match `:96`).

## LOW

### R3-3 [LOW · CONFIRMED] `snowsight_profile_column` pins a failed context probe for the whole session
`app/ui/components.py:310`
A transient org/account probe failure writes `ctx=('','')` to
`st.session_state['_ow_snowsight_ctx']` **unconditionally**; the not-None guard then permanently
short-circuits the metadata-tier retry that would self-heal → no "Open in Snowsight" profile links
on any query-history table until a full browser reload. Same commit-on-failure anti-pattern already
fixed in `current_role()` (`session.py:164-168`); this call site was missed.
**Fix:** cache `ctx` only when `res.usable()`; else return `df, {}` without writing session_state.

### R3-4 [LOW · CONFIRMED] Failure counters use `= 'FAIL'`, dropping INCIDENT-status failures
`app/data/ops_sql.py:38`, `ops_sql.py:79`, `app/data/insights_sql.py:164`, `app/data/mart_sql.py:476`
`EXECUTION_STATUS = 'FAIL'` omits the third completed status (INCIDENT). The documented internal
standard is `<> 'SUCCESS'` = fail+incident (`change_impact_sql.py:164-167`), applied at the
change-impact/release builders. So an INCIDENT query counts in QUERY_COUNT but not FAILED_COUNT, and
the Operations failure KPI reads lower than the change-impact view for the same period. (Token is
correct — `FAIL`, not `FAILED` — the defect is the missing bucket vs the convention.) INCIDENT is
rare, so magnitude is marginal.
**Fix:** standardize the four surfaces to `EXECUTION_STATUS <> 'SUCCESS'`.
**DEFERRED to V062 (parity):** verified that `FACT_QUERY_HOURLY`'s loader (`V002:132`) counts
`= 'FAIL'`, and `ops_sql.query_window_summary`/`failures_by_error` are the **live fallbacks**
of that mart — so an app-only change would make live count fail+incident while the mart counts
fail-only, a mart-vs-live divergence. The clean fix changes the app builders AND their mart-loader
twins together (a migration). Tracked on the V062 task.

### R3-5 [LOW · CONFIRMED] Bulk-ACK audit INSERT over-selects already-ack'd events (false ACK record)
`app/ui/pages/alerts.py:101`
The ACK-branch UPDATE transitions only `STATUS='OPEN'`, but the audit SELECT matches any selected
event now in `STATUS='ACK'`. Since the feed offers `('OPEN','ACK')`, an already-ACK event is a
UPDATE no-op yet gets a fresh `ACTION='ACK', ACTED_BY=<actor>` audit row — a false, duplicate
acknowledgement recording an act that didn't happen. Legacy split path only (SP_ALERT_LIFECYCLE
absent); RESOLVE branch unaffected; no effect on actual event state.
**Fix:** scope the ACK audit SELECT to events the UPDATE actually transitioned (prior-status OPEN /
the just-stamped actor+timestamp), not any event now in ACK.

### R3-6 [LOW · CONFIRMED] Closed-loop reverse-hint labels an auto-suspend fix as a cluster-range change
`app/ui/pages/alerts.py:292`
A two-way ternary `'STATEMENT_TIMEOUT' if … else 'CLUSTER_RANGE'`: the auto-suspend fix statement
contains neither token → falls to CLUSTER_RANGE → the operator is told to reverse
MIN/MAX_CLUSTER_COUNT for a change that modified AUTO_SUSPEND. The correct 'AUTO_SUSPEND' lead-dict
key exists but is unreachable. Advisory caption only — executed SQL, REMEDIATION_LOG, and
SAVINGS_LEDGER are all correct.
**Fix:** make the kind selection three-way (key off `fix_kind` or detect `'AUTO_SUSPEND' in stmt_cl`).

### R3-7 [LOW · CONFIRMED] MTD-vs-prior pace delta includes today's partial day, biasing it low
`app/logic/formulas.py:274` (`mtd_pace_vs_prior_month`) → Overview `_mtd_pace_kpi`
The current-side equal window spans days 1..today **inclusive** (partial today) vs the prior side
1..N all complete, so the "MTD vs last month (same days)" KPI reads negative/under-pace when spend
is actually flat; bias grows toward midnight and resets each morning. The exclude-the-partial-day
standard is applied at the sibling window-vs-prior functions and in `complete_days_only` (B4) but
not here. The displayed full-month MTD value is correct — only the pace delta is biased.
**Fix:** base the equal window on completed days (`eff_day = today.day - 1`) / add
`& (frame["DAY"] < today)` to the current-side filter; leave the full-month `mtd` value unchanged.

## Systemic theme
**"Established convention duplicated inline, then missed at a new call site"** — 4 of 7 are a
canonical read/normalization or failure-handling rule correctly applied at sibling sites but
open-coded and skipped at one more: read-normalization drift (cache-% ×100 R3-2, `<> SUCCESS` R3-4,
exclude-partial-day R3-7) and commit-on-failure / all-clear-on-error (snowsight ctx R3-3, triage
banner R3-1). Systemic remedy worth considering: centralize behind shared helpers
(`cache_pct(col)` SQL fragment, `failed_query_predicate()`, `completed_days_filter()`, a
"cache only when `res.usable()`" probe wrapper) + a grep-based CI guard for raw
`PERCENTAGE_SCANNED_FROM_CACHE` without `*100`, `EXECUTION_STATUS = 'FAIL'`, and unconditional
`session_state[...] =` after a `.usable()` check.
